# Book Club — Phase 6 구현 계획

## 1. 배경 및 목표

Phase 5(`v0.2.0`)에서 기술 부채 정리(Riverpod 3.x, freezed 3.x), 독서 통계 심화, ML 추천, 소셜 공유 루프를 완료했다.

Phase 6는 **실시간 소셜** 레이어를 구축한다:

1. **그룹 채팅 인프라**: WebSocket 기반 실시간 메시지 파이프라인 — Phase 4에서 그룹 기능을 만들었지만 채팅이 없었다.
2. **그룹 채팅 UI**: 메시지 CRUD, 읽음 처리, 파일/이미지 공유.
3. **실시간 인앱 알림**: WebSocket 연결을 통한 인앱 알림 + FCM 심화(토픽 구독, 배치 전송).

Phase 7 이후를 위해 딥러닝 추천 파이프라인의 데이터 수집 스키마(user_event_log)를 이번 인프라 단계에서 미리 열어둔다.

## 3. M23 — WebSocket 실시간 인프라

### 3.1 목표

그룹 채팅과 실시간 알림이 공유할 WebSocket 파이프라인을 구축한다.
채팅 메시지 전송뿐 아니라 알림, 읽음 처리, 타이핑 인디케이터 등 모든 실시간 이벤트가 이 레이어를 통한다.

### 3.2 백엔드 아키텍처

```
Client ──WS──▶  FastAPI WS Handler
                   │
                   ├── ConnectionManager (in-memory, 단일 워커 용)
                   │       └── {club_id: set[WebSocket]}
                   │
                   └── Redis Pub/Sub (다중 워커 브로드캐스트)
                           topic: ws:club:{club_id}
                           topic: ws:user:{user_id}
```

**핵심 결정:**
- 초기: 단일 워커 + Redis pub/sub으로 수평 확장 경로 확보
- 메시지 포맷: JSON `{type, payload, ts}` — type은 `chat.message | notification | typing | read_receipt`
- 인증: 쿼리 파라미터 `?token=<jwt>` (WS는 헤더 미지원)
- 연결 유지: 30초 ping/pong 하트비트

### 3.3 구현 범위

**백엔드:**
```
POST /clubs/{club_id}/messages          — 메시지 생성 (REST + WS 브로드캐스트)
GET  /clubs/{club_id}/messages          — 이전 메시지 페이지네이션
WS   /ws/clubs/{club_id}?token=<jwt>   — 클럽 채팅 WebSocket
WS   /ws/me?token=<jwt>                — 개인 알림 WebSocket
```

**신규 테이블:**
```sql
club_messages (
    id          UUID PK,
    club_id     UUID FK clubs.id,
    user_id     UUID FK users.id,
    content     TEXT,
    media_url   TEXT,
    created_at  TIMESTAMPTZ DEFAULT now(),
    edited_at   TIMESTAMPTZ,
    deleted_at  TIMESTAMPTZ   -- soft delete
)

message_reads (
    message_id  UUID FK club_messages.id,
    user_id     UUID FK users.id,
    read_at     TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (message_id, user_id)
)

user_event_log (               -- Phase 7 딥러닝 데이터 수집
    id          UUID PK,
    user_id     UUID FK users.id,
    event_type  VARCHAR(64),   -- "book_viewed", "session_started", etc.
    payload     JSONB,
    created_at  TIMESTAMPTZ DEFAULT now()
)
```

**모바일:**
- `web_socket_channel` 패키지 연결 레이어
- `ClubChatNotifier` (@riverpod, keepAlive) — WebSocket 연결 수명 관리
- 재연결 로직 (exponential backoff)

### 3.4 테스트
- WebSocket 연결 인증 실패 → 403 Closed
- 메시지 브로드캐스트: 동일 클럽 2개 연결에 모두 수신
- Redis pub/sub 페일오버: Redis 없을 때 단일 워커 fallback

## 4. M24 — 그룹 채팅 UI

### 4.1 목표

WhatsApp/KakaoTalk 수준의 기본 채팅 UX. 책 클럽 맥락에 맞게 하이라이트 인용 기능 추가.

### 4.2 구현 범위

**채팅 화면 (`club_chat_screen.dart`):**
- 역순 `ListView.builder` (최신 메시지 하단)
- 말풍선 UI: 내 메시지(우측, accent), 상대 메시지(좌측, surfaceVariant)
- 타임스탬프 + 읽음 수 표시
- 이미지/파일 첨부 (Cloudflare R2 업로드)
- 롱프레스: 답장, 복사, 삭제

**하이라이트 인용:**
- 채팅창 내 "하이라이트 공유" 버튼 → 내 하이라이트 선택 → 인용 카드로 전송

**클럽 상세 (`club_detail_screen.dart`) 연결:**
- 기존 화면에 "채팅" 탭 추가

### 4.3 테스트
- 메시지 전송 → WS 브로드캐스트 → UI 즉시 반영
- 오프라인 → 온라인 복귀 시 미수신 메시지 페이지네이션 보충

## 5. M25 — 실시간 알림 + FCM 심화

### 5.1 목표

인앱 알림을 WebSocket으로 실시간화하고, FCM 배치 전송과 토픽 구독을 완성한다.

### 5.2 구현 범위

**백엔드:**
```
WS /ws/me?token=<jwt>  — 개인 알림 스트림 (M23에서 엔드포인트만 열고 여기서 완성)
POST /me/notifications/read-all   — 전체 읽음 처리
FCM 토픽: "club:{id}" — 클럽 구독자 일괄 전송
FCM 배치: 최대 500 토큰/요청 (HTTP v1 멀티캐스트 에뮬레이션)
```

**모바일:**
- `NotificationNotifier` WebSocket 이벤트 수신 시 뱃지 카운터 실시간 업데이트
- FCM 포그라운드 핸들러: `firebase_messaging` 패키지 연결 (현재 스텁)
- 알림 탭 무한 스크롤 (cursor-based)

### 5.3 테스트
- WS 알림: 팔로우 이벤트 → 즉시 인앱 알림
- FCM 오프라인: 앱 백그라운드 시 푸시 수신

## 7. 아키텍처 고려사항

### 7.1 WebSocket 수평 확장

단일 워커에서 시작하되 Redis pub/sub을 추가해 Fly.io 다중 머신 배포 시 메시지 팬아웃이 가능하도록 설계.

### 7.2 user_event_log 수집 전략

Phase 7 딥러닝을 위해 M23에서 테이블만 만들고, 중요 이벤트(book_viewed, session_started, highlight_saved, recommendation_clicked)를 비동기 백그라운드 태스크로 기록. 쿼리 경로에 포함하지 않아 성능 영향 없음.

### 7.3 보류 항목 (Phase 7 이후)

- **(discovery) 딥러닝 추천**: user_event_log 6개월 이상 누적 + 활성 사용자 1만 이상 시 검토.
- **(club) 음성/영상 통화**: WebRTC 별도 시그널링 서버 필요.

## 8. 오픈 퀘스천

1. **WebSocket 서버 분리**: 채팅 트래픽이 커지면 별도 서비스(Fly.io machine)로 분리할 것인가? — 초기에는 단일 FastAPI 앱 내에서 처리, 분리는 Phase 7 결정.
2. **메시지 암호화**: E2E 암호화 필요 여부 — 초기 서버 사이드 저장, 법적 검토 후 E2E 도입.
3. **첨부파일 크기 제한**: 이미지 10MB, 기타 파일 50MB로 시작.
